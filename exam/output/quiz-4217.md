D** [Visualization · Hydra architecture — three main parts] — The corpus states: 'A scene delegate, which provides the scene information; The render index, which keeps track of changes and manages the scene; The render delegate, which uses the render index and scene delegate to visualize scene information to create the final image.' The other options swap roles, rename parts, or use non-USD terminology.

**49. D** [Data Exchange · File format plugins as USD integration mechanism] — The corpus states that file format plugins allow 'An OpenUSD stage can include a source file format directly as a reference, payload or sublayer. The source file format is translated on the fly, while it is read as a USD document,' and crucially that 'The source file format can remain the source of truth.' Standalone converters produce a separate output file and require a pre-export step. DCC importers translate from OpenUSD into the application's runtime format — the opposite direction. DCC exporters translate from the application's runtime format to OpenUSD, also requiring a pre-export step and not retaining the original format as the source of truth.

**50. D, E** [Data Modeling · automatic vs manual unit reconciliation] — The corpus states timeCodesPerSecond is automatically reconciled during composition: 'USD automatically scales time samples so animations play back correctly relative to the root layer's timeCodesPerSecond.' The same automatic scaling applies through layer offsets. metersPerUnit, upAxis, and kilogramsPerUnit are listed as 'Manually Handled' — the assembler is responsible for corrective transforms.

**51. A** [Data Modeling · custom attribute namespace convention for grouped data] — The corpus states: 'Since USD doesn't have a native struct type, namespace-prefixed attributes serve as the standard convention for representing this kind of grouped data.' The example demonstrates acme:sensor:temperature / humidity / pressure. customData is a composable dictionary described as more costly for composition; a Scope child adds unnecessary hierarchy; a string attribute loses type safety.

**52. D** [Pipeline Development · model hierarchy — assembly and component kind relationships] — The page states that 'component models cannot contain other component models as descendants.' The component kind denotes a leaf asset or pruning point in the model hierarchy. Descendants can use subcomponent for important prims that are outside the model hierarchy, but another component kind as a descendant is forbidden. The option requiring all descendants to be subcomponent overstates the rule. The option permitting group descendants below a component inverts the hierarchy direction — groups and assemblies are ancestors, not descendants. The option permitting assembly descendants is also contradicted by the leaf-boundary rule.

**53. B** [Pipeline Development · asset parameterization — variant sets vs primvars and scenegraph instancing] — The page states directly: 'Variations in variant selections will generate new prototypes for downstream contexts, while primvars will not.' This makes parameterization through primvars the lighter choice for single property parameters, offering upfront memory savings at the cost of additional lookups in materials. The option inverting the two behaviors misattributes prototype generation to primvars. The option claiming both generate prototypes per value is contradicted for primvars. The option claiming both share a single prototype is contradicted for variant selections.

**54. D, E** [Debugging and Troubleshooting · 6.1] — Composition is cached as a prim-level index for fast access, while the USD core does not pre-compute or cache per-composed-property values, and clients can construct and retain a UsdAttributeQuery or UsdResolveInfo to speed repeated queries on an attribute. GetPropertyStack is documented for debugging only, not as a resolution path. How data combines during value resolution is specific to each metadatum and varies by data type — dictionaries, for example, merge element by element — so it is not identical across metadata. And it is composition that is internally multi-threaded; value resolution is designed to be efficiently multi-threaded by clients, not scaled by opening many stages in parallel.

**55. C** [Composition · defaultPrim — behavior when unset during referencing] — The source states: 'If no defaultPrim is set then when the above .usda is brought in as a payload or reference it will resolve as an empty layer and output a warning message in the log.' The fatal-error distractor overstates severity. The both-prims distractor misapplies multi-prim grafting, which requires explicit authoring. The first-prim distractor invents an implicit selection rule that does not exist.

**56. B, C** [Customizing USD · IsA vs API schema — assignment and identification] — The corpus states: 'We use the typeName metadata to assign an IsA schema to a prim' and 'each prim can only subscribe to one IsA schema at a time.' API schemas 'do not assign a typeName to a prim. Instead, are list-edited in the apiSchemas metadata.' The second option swaps the query methods; the fourth inverts the concreteness rule; the fifth is incorrect because typeName exclusively identifies IsA schemas.

**57. C** [Visualization · 8.3] — A reference composes the defaultPrim's subtree, so a material prim outside that encapsulated hierarchy does not exist in the new context and the binding cannot resolve. The relationship itself is still composed rather than discarded, references do not copy out-of-hierarchy prims into the target stage, and binding strength is authored metadata that composition never demotes.

**58. C, D, E** [Customizing USD · 3.5] — USDC is the compressed binary Crate format suited to fast loading and numerically heavy data while USDA is human-readable ASCII; USDZ is an atomic, uncompressed zipped archive meant as read-only packaging and delivery, ideal for XR; and a .usd file can be either encoding, so it can change without breaking references. The completeness claim is wrong because any other 3D format can be loaded through file format plugins without prior conversion. The USDA-for-heavy-geometry claim is wrong because binary crate, not ASCII text, is preferred for large geometry layers.

**59. D** [Composition · variant operations — lightweight vs heavyweight switches] — The source states that lightweight variant operations include 'Changing attribute values - For example, switching a color from red to blue' because 'USD doesn't need to rebuild the composed scene structure. The stage's composition index remains the same.' Swapping referenced layers is explicitly listed as heavyweight because it changes the composition structure. Changing activation opinions is also listed as heavyweight. Introducing new sublayer arcs would change composition structure.

**60. C** [Customizing USD · schema versioning — version identifier encoding] — The corpus states: 'The schema version will be embedded in the schema identifier itself as a suffix, e.g. "SphereLight_2" is version 2 of the SphereLight schema.' It further states: 'Version 0 of a schema will be represented without a version suffix. For example "SphereLight" is version 0 of SphereLight; "SphereLight_0" will not be allowed as a schema identifier.' The underscore-zero form and other separator styles are therefore incorrect.
